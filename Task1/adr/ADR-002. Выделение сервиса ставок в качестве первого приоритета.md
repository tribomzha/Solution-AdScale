# ADR-002 : Выделение сервиса ставок в качестве первого приоритета


**Дата:** 2026-07-26

**Статус:** Accepted

## Контекст

AdScale готовится к подключению dsp-платформы, повышая нагрузку на системы и НФТ. Текущая система - монолит на зоопарке языков с одной репликой PostgreSQL без возможности гибкого масштабирования под растущую нагрузку. Система работает на пределе и не удовлетворяет собственным НФТ.

Ключевые архитектурные драйверы:
- Нагрузка: 18K RPS в пике в монолите, P95 задержка < 80 ms + запас на пики
- Доступность: SLA 99,9%
- Сроки: 3 месяца до подключения dsp
- Команда: backend-, frontend- и DevOps-разработчики
- DevOps: деплой вручную, 1 прод кластер

Рассматривались три альтернативы:
1. Рекламный (Ставок) сервис
2. Сервис аукциона
3. Сервис выдачи
4. Сервис статистики
5. Финансовый сервис
6. Сервис аналитики
7. Рекламный кабинет

### Альтернатива 1: Рекламный сервис
Плюсы: критичен по latency, высокая нагрузка, испытывает проблемы по производительности, развязывание по БД
Минусы: влияние на смежные сервисы

### Альтернатива 2: Сервис аукциона
Плюсы: критичный сервис, развязывание по БД
Минусы: влияние на смежные сервисы

### Альтернатива  3:  Сервис выдачи
Плюсы: синхронная запись показов/кликов, часть главного функционала
Минусы: влияние на смежные сервисы, простота в сценариях, не испытывает проблемы по производительности

### Альтернатива 4: Сервис статистики
Плюсы: развязывание по БД и избавление от тяжелых запросов в БД
Минусы: влияние на смежные сервисы, возможно снизить влияние на производительность другими методами
### Альтернатива 5: Финансовый сервис
Плюсы: развязывание по БД
Минусы: влияние на смежные сервисы

### Альтернатива 6: Сервис аналитики
Плюсы: развязывание по БД
Минусы: влияние на смежные сервисы

### Альтернатива 7: Рекламный кабинет
Плюсы: развязывание по БД, перенос нецелевой логики работы с оплатой
Минусы: влияние на смежные сервисы


## Решение

В качестве первого приоритета на вынос принят Рекламный сервис.

## Последствия

**Положительные:**
- снижение влияние за конкуренцию в compute
- возможность гибкого масштабирования и балансировку под растущую нагрузку и соблюдение SLA
- снижение влияния работы сервиса на производительность БД

**Отрицательные:**
- затраты на ресурсы
- сложность выделения доменного контекста
- штраф за сетевые взаимодействия
- необходимость применения паттернов микросервисной архитектуры (AGW, ServiceMash)
- сложность в расследовании инцидентов и отладке


**Риски:**
- рассогласованность данных для таргетинга
- неудачное проведение границ
- сохранение сильной связанности с оставшимся монолитом и скатывание в распределенный монолит
