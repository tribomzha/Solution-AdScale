## ADR-003. Выбор технологии для потоковой обработки событий.

**Дата:** 2026-07-26

**Статус:** Accepted

## Контекст

AdScale готовится к подключению dsp площадки. В ходе работы собирается статистика показов и кликов по рекламе. Сейчас запись происходит синхронным вызовом сервисом доставки сервиса статистики, который напрямую пишет в единственную PostgreSQL.

Ключевые архитектурные драйверы:
- Нагрузка: 18K RPS в пике в монолите, P95 задержка < 100 ms
- Консистенция: нулевая потеря данных статистики (критично для бизнеса)
- Доступность: SLA 99,9%
- Сроки: 3 месяца до подключения dsp
- Команда: backend-, frontend- и DevOps-разработчики
- DevOps: деплой вручную, 1 прод кластер

Рассматривались три альтернативы:
1. kafka 
2. RabbitMQ
3. ActiveMQ

### Альтернатива 1: kafka
Плюсы: pull-модель, высокая производительность и масштабируемость, отказоустойчивость и долговременное хранение
Минусы: высокие затраты на ресурсы, отсутствие встроенного продвинутого мониторинга

### Альтернатива 2: Модульный монолит
Плюсы: надежность доставки, поддержка различных протоколов, гибкая маршрутизация, масштабирование за счет потребителей
Минусы: ограничение при высоких нагрузках (есть нюансы при горизонтальном масштабировании), избыточен для простой задачи

### Альтернатива 3: ActiveMQ
Плюсы: надежность доставки, гибкость в интеграции, активное сообщество
Минусы: ограничения по масштабированию, проблемы со стабильностью

## Решение

В качестве брокера сообщений будет использоваться kafka.

## Последствия

**Положительные:**
- сервис собирающий статистику не зависает при записи
- в случае увеличения нагрузки возможно гибкое горизонтальное масштабирование
- возможность восстановить данные в случае проблем на сервиса статистки

**Отрицательные:**
- затраты на ресурсы
- сложность настройки
- отсутствие встроенного мониторинга, а значит необходимо подбирать соответствующие решения


**Риски:**
- при большом количестве данных и длительном хранении могут потребоваться большие ресурсы Disk 
- ошибки при настройке, которые негативно повлияют на функционал
- при большом количестве ошибочных сообщений потребуется большая работа саппорта при исправлении
