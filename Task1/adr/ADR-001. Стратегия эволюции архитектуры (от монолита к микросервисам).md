# ADR-001: Стратегия эволюции архитектуры (от монолита к микросервисам)

**Дата:** 2026-07-26

**Статус:** Accepted

## Контекст

AdScale готовится к подключению dsp-платформы, повышая нагрузку на системы и НФТ. Текущая система - монолит на зоопарке языков с одной репликой PostgreSQL

Ключевые архитектурные драйверы:
- Нагрузка: средний 50K RPS , P95 задержка < 80 ms
- Доступность: SLA 99,9%
- Сроки: 1 год
- Команда: backend-, frontend- и DevOps-разработчики
- DevOps: деплой вручную, 1 прод кластер

Рассматривались 5 альтернатив:
1. Strangler Fig
2. Big Bang
3. Parallel Run
4. Incremental Decomposition по доменам
5. Branch by Abstraction

### Альтернатива 1: Strangler Fig
Плюсы: отсутствие простоя, постепенное освоение практик CI/CD, observability, service mesh, API Gateway, естественная эволюция границ
Минусы: длительный срок миграции, двойная поддержка, сложная маршрутизация и версионирование, риск распределенного монолита

### Альтернатива 2: Big Bang
Плюсы: быстрый переход к целевой архитектуре, отсутствие двойной поддержки, чистый старт, упрощенная маршрутизация
Минусы: высокие риски простоя из-за дефектов, наличие периода отладки, высокие требования к тестированию.

### Альтернатива 3: Parallel Run
Плюсы: максимальная валидация функционала, т.к. есть текущий, возможность канареечного переключения
Минусы: повышенная нагрузка на инфраструктуру, не подходит для операций с сайд‑эффектами, нужна специальная инфраструктура (фреймворк для сравнения ответов, дублирование трафика, дополнительные логи и алерты)

### Альтернатива 4: Incremental Decomposition по доменам
Плюсы: фокус на бизнес‑ценности, чёткие границы ответственности, естественный путь к асинхронности
Минусы: требует зрелого DDD, риск несогласованности данных, долгая стабилизация контрактов, операционная сложность

### Альтернатива 5: Branch by Abstraction
Плюсы: минимальный риск рефакторинга, подходит для сильно связанного кода, плавный перенос реализации, хорошо сочетается с асинхронностью
Минусы: временная сложность архитектуры (абстракции), не решает проблему общей БД автоматически, зависит от дисциплины команды

## Решение

AdScale будет эволюционировать по стратегии Strangler Fig. Применяются следующие принципы:
- Монолит преобразуется в модульный монолит
- Самый высоконагруженный модуль выносится как отдельный сервис и добавлен API Gateway
- Добавлены health check и readiness точки для подготовки
  к будущему выделению в микросервисы
- БД разделены по доменам

## Последствия

**Положительные:**
- возможность продолжать работу без изменений на стороне потребителей
- постепенное освоение практик CI/CD, observability, service mesh, API Gateway
- естественная эволюция границ

**Отрицательные:**
- длительный срок миграции, 
- двойная поддержка, 
- сложная маршрутизация и версионирование, 
- риск распределенного монолита
- - Команда должна соблюдать дисциплину доменных границ

**Риски:**
- риск скатиться в распределнный монолит
- неудачные границы доменов/сервисов
- проблема согласованности данных
- Рост числа сервисов и падение наблюдаемости
- Усложнение CI/CD
- Двойная поддержка и рост технического долга
